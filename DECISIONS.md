| 2026-11-14 | Relation types are named and directed so every question path is traversable outgoing-only: `OWNS` → `OWNED_BY` (Service→Team), `ON_CALL_FOR` → `ON_CALL` (Team→Person), `CUSTOMER_OF` → `SERVES` (Service→Customer); `DOCUMENTED_BY` added for Runbook | HydraDB path search is directed and takes one relationship type per MATCH pattern, and our searches run `relDirection: 'outgoing'` from the question's seed entity, so an edge pointing the other way is unreachable. `ON_CALL` is single-valued per team so `page_owner` has one gold answer instead of a refused tie. | PRD §4, §6, REALITY_SPIKES S4/S5, src/trailmend/graph/schema.py |
| 2026-11-14 | Node natural keys carry the seed (`team:s7-aurora`, not `team:aurora`) | Ids are a hash of the natural key, so two seeds that drew the same name produced the same id and silently merged into one node when loaded into the same HydraDB graph — the first load of seed 7 after seed 1 added 893 nodes instead of 1165. Seeds are now disjoint in ids and edges and can share one graph. | evidence/load.json, tests/unit/test_northwind_generator.py |
| 2026-11-14 | The quarantine window (`recent`) is stored on the edge as a string of C and B codes, not kept in process memory | `should_quarantine` reads the last `window` judgements, so blame has to accumulate across rounds and survive a restart. Holding it in memory would also leave the product API unable to quarantine anything. A missing property reads back as null (S20), so the column was added without a migration. | PRD §6, src/trailmend/graph/state.py |
| 2026-11-14 | C3a settled before any Mend run: a template whose gold is a set returns every answer tied at minimum cost (costs compared after rounding to 1e-9); correct means the returned set exactly equals gold, and set-F1 is reported alongside. Single-answer templates still refuse a tie as `ambiguous_answer`. Credit for a set answer: blame the chosen path of each wrong member, confirm the cheapest gold path of each missed gold member, confirm the path of each correct member. | PRD §7 step 2 says ties refuse, PRD §9 says set-F1 is reported for multi-answer templates; at round 0 this left 31 of seed 7's 340 held-out questions refused purely because every edge still costs 1.0. Refusing them would have measured the tie-break rule, not the Mend. | docs/TASKS.md C3a, PRD §7, §9, user decision 2026-11-14 |
| 2026-11-14 | INV6 reads as: each random arm mirrors the mechanism arm it controls, not the whole `full` plan. `random_reweight` makes exactly the reweights `full` planned this round — same count, same signal tuple per change, so same magnitude and direction — on edges drawn without replacement from the graph's edges by a seeded RNG, and no quarantines. `random_quarantine` likewise mirrors only `full`'s quarantines. Their question ids are prefixed `random:` in the receipts. | A control has to isolate one mechanism. A single random arm carrying both reweights and quarantines would answer "does any change of this size help?" but could not say which half of the Mend the effect came from, and the task names two random arms pairing with `reweight_only` and `quarantine_only`. The `random:` prefix keeps a random receipt from ever reading as real credit for an edge. | docs/TASKS.md D3, tests/unit/test_mend_policies.py, tests/live/test_round.py |
| 2026-11-14 | `quarantine_only` applies the quarantines `full` planned but not the cost changes, which means its `recent` window never fills across rounds, so it can only quarantine on blame concentrated inside a single round. | The quarantine test reads the persisted `recent` window, which only grows when a reweight is applied. Applying reweights to make quarantine fire would stop the arm being an ablation of reweighting. The arm is weaker by construction and is reported as such rather than silently helped. | src/trailmend/loop/policy.py, src/trailmend/core/update.py `should_quarantine` |
| 2026-11-15 | Promotion compresses any **contiguous sub-path of at least two hops** that was confirmed by `promote_min_questions` distinct questions, not only the whole confirmed path. The shortcut still has the PRD's `SC_<TEMPLATE>` type, runs from the sub-path's first node to its last, and carries its `via_path`. | Measured before building it: on seed 1, round 0, no whole path is confirmed by more than one question (242 distinct paths, best = 1), because the generator makes one question per seed entity per template. The rule as written in PRD §7 step 7 can therefore never fire and `promote_only` would have been a dead arm. Confirmed sub-paths do repeat: 8 reach the threshold of 3, every one an `OWNED_BY → ON_CALL` tail shared by the alerts on one service — exactly the compression the mechanism is for. | REALITY_SPIKES S24, PRD §7 step 7, src/trailmend/core/promote.py |
| 2026-11-15 | A new shortcut starts at the summed cost of the hops it compresses, not at 1.0. | Promotion then cannot change any answer in the round it happens: the shortcut ties with the path it replaces, so it only shortens the route. Starting at 1.0 would have made a freshly promoted 3-hop path cheaper than every rival answer the moment it was created, and the arm would have measured that gift rather than compression. The shortcut earns its own confirms and blames afterwards like any edge. | src/trailmend/core/promote.py, tests/unit/test_promotion.py, tests/live/test_round.py |
| 2026-11-15 | A shortcut's endpoint labels come from its `via_path` (first hop's source label, last hop's target label) and its terminal label is stored on the edge as `target_label`; `SC_` types are not in the static `ENDPOINTS` table. | Sub-path promotion means one `SC_<TEMPLATE>` type can join different label pairs (`SC_PAGE_OWNER` compressing an `OWNED_BY → ON_CALL` tail runs Service→Person, not Alert→Person), so a static per-template endpoint pair would have been wrong. Path rows carry relationship properties (S23), so the answer path reads `target_label` with no extra query. | REALITY_SPIKES S23, src/trailmend/graph/schema.py |
| 2026-11-15 | An edge's lifecycle is one receipt stream: `EdgeStatus` gained `absent`, and promotion and retirement are `Change` variants whose before/after states are an absent and a live edge. | `/v1/receipts` and the rollback button have to work for every change the Mend makes, and INV3 (apply then rollback leaves the edge identical) has to cover shortcuts too. Giving shortcuts their own side channel would have left them outside both. Rolling back a promotion deletes the edge; rolling back a retirement restores it whole, via_path and counters included. | src/trailmend/core/model.py, src/trailmend/core/update.py, tests/unit/test_promotion.py |
| 2026-11-15 | Gap-fill ingests exactly the pool documents that mention the gap's seed entity, one wave, no expansion to newly reached nodes. | PRD §7 step 8 says "only documents mentioning the seed entity (never the gold)". Measured first: that rule makes 35 of seed 1's 96 unreachable questions reachable, so it is worth building; a second wave would reach 43 but widens what the Mend may read for a question it has already failed, and the narrow rule is what INV7 is written against. The extra wave is in ROADMAP as not built. | REALITY_SPIKES S25, PRD §7 step 8, src/trailmend/loop/gapfill.py |
| 2026-11-15 | The plain_store baseline gets its `top_k` tuned to its best held-out accuracy (swept on seed 1, fixed at 15 for every seed); the Mend's constants stay frozen in `config/mend.toml` from before the first run. | An unflattering baseline proves nothing. k=5 scored 0.1706 on seed 1 and k=15 scores 0.2647, so quoting the first would have inflated the gap by nearly ten points. Tuning on held-out is an advantage the graph arm is not given, and the asymmetry is stated wherever the number appears. | evidence/plain_store.json, src/trailmend/eval/plain_run.py |
| 2026-11-15 | A hypothesis is never decided from an empty input: the analysis refuses a (seed, arm) that recorded curve rows but has no held-out tape, naming the missing path, and `hypotheses()` raises rather than deciding H4 or H5 with no quarantine reports or no break rows. | Found by dry-running the analysis with a wrong `run_id`: the tape and receipt readers return empty when a file is absent, so H5 came out **PASS** with a worst break share of 0.0 and H4 came out **PASS** over an empty list of recalls. A missing measurement had been reading as a good result, which is exactly the silent fallback the build contract bans. With the real run id the same data gives H5 FAIL. | docs/BUILD_CONTRACT.md, src/trailmend/eval/analyse.py, tests/unit/test_analysis_refusals.py |
| 2026-11-15 | INV6 is checked on the recorded rows before any curve is produced: `analyse` refuses to write a file unless, in every control round, the random arm applied exactly the number of changes the Mend planned in that same round of that same arm, and none of the mechanism it does not control. The comparison is within an arm, not against `full`'s counts in the same round. | Each arm resets the graph and evolves on its own, so `full` round 2 plans 587 reweights from full's graph while `random_reweight` round 2 plans 572 from its own: a cross-arm equality cannot hold and would stop being an ablation if it did. Within an arm the equality is exact on the recorded run — 10 control rounds for seed 1, every one matching — which is the claim the curve rests on. | user constraint 2026-11-14, src/trailmend/eval/analyse.py `check_inv6`, tests/unit/test_analysis_refusals.py |
| 2026-11-15 | A measured run claims `evidence/.measuring.json` with its own pid for as long as it is writing, and the live and API test fixtures skip with that run's id in the reason while the claim is held. A stale claim (pid gone) is ignored, so a crashed run cannot block the tests. The claim is written by the writing process itself — never by hand, because a hand-written pid is exactly what failed. | Twice now a measured arm was contaminated by something else writing to the same graph: the API tests during seed 1 `reweight_only`, and the whole live suite during seed 7 `random_quarantine`, the second time because I wrote the lock file manually with a pid that had already exited, so the guard saw a stale claim and let the tests run. The token for the local HydraDB is scoped to `default/graphs/default` (a write to `default/graphs/tests` is refused 403), so a separate graph id for tests is not available without a differently scoped token; serialising on a claim is the isolation that was actually achievable. | src/trailmend/eval/measuring.py, tests/live/conftest.py, tests/api/conftest.py, tests/unit/test_measuring_lock.py |
| 2026-11-15 | The matched-control design is published, not just asserted: `evidence/changes.json` carries every arm's planned and applied change counts per seed and round, and `/evidence` renders them as a table per seed with `full` and each control in adjacent columns, the planned counts on hover. | A reader cannot check "the controls make the same number and size of changes" from a curve. Side by side it is one glance: round 2 of seed 1 shows `full` 587 reweights and 8 quarantines against `random_reweight` 572 reweights and 0 quarantines, each equal to what the Mend planned in that arm's own round. The arms differ because each resets the graph and evolves separately, which the panel says in words so the difference is not mistaken for a broken control. | user request 2026-11-15, src/trailmend/eval/analyse.py `change_counts`, apps/web/components/Changes.tsx |
| 2026-11-15 | The API loads G0 itself when the demo graph has no nodes at startup, in a background thread, writing the same reset receipt the admin endpoint writes. | The hosted graph was empty from the day it was created: every `/v1/ask` on the live site answered `unreachable`, so the two pages a judge is pointed at had nothing to show, and the only way to fill it was an admin token nobody carries. A graph that loads itself needs no secret and no runbook. It runs off the request path so a slow or unreachable HydraDB delays nothing and the service still serves evidence; when the graph already has nodes it does nothing at all, which two api tests pin down. | src/trailmend/api/demo.py, tests/api/test_api.py |
| 2026-11-15 | E6 ran 8 concurrent clients x 7 asks a pass against the hosted API, 56 requests a pass, deliberately under the public 60-asks-a-minute limit, instead of raising the limit for the measurement. | The rate limit is a product decision on a public demo, and a load run that mostly answers 429 measures the limiter, not the graph. Staying under it gives percentiles of real answers: 0 rate-limited responses in either pass, 52 answers and 4 `unreachable` (questions whose edge is in the withheld pool). The cost is the sample size — p99 over 56 points is one request — and a larger run needs `TRAILMEND_ASK_RATE_PER_MINUTE` raised on the deployment first. | evidence/latency.json, src/trailmend/eval/load.py, REALITY_SPIKES S34 |
| 2026-11-15 | Run 1 stays published as a failure and is not re-run, re-scored or withdrawn. Run 2 is a second run beside it, on a second dataset version, preregistered in PRD §3.2 before any code was changed. | The headline hypothesis failed and the run is the honest record of a design that was fixed before measuring. Re-running it with a changed generator or a changed update rule and publishing only the better number is the exact move the build contract exists to prevent. Keeping both means the diagnosis is checkable: a reader can see what was claimed, what happened, and what was changed in response. | user instruction 2026-11-15, docs/RUN1_DIAGNOSIS.md, evidence/hypotheses.json, PRD §3.1 |
| 2026-11-15 | Dataset v2 splits the planted wrong edges into `contradicted` (0.4; the true edge stays in G0 at cost 2.0 beside the wrong one at 1.0), `recoverable` (0.3; the true edge is withheld into the pool with its document) and `destroyed` (0.3; run-1 behaviour, unrepairable). The kind is written into `faults.json`. | Measured, not assumed: on all three seeds the true competing edge for a planted wrong edge is in G0 **0** times, in the pool **0** times and nowhere **13** times, and the documents are rendered from G0, so the corpus corroborates the wrong version. Perfect oracle quarantine of every planted wrong edge is therefore worth **+0.0 accuracy on every seed** — it converts 13 wrong answers into 13 refusals. Run 1 asked a repair mechanism to fix damage that contained no recoverable truth. v2 keeps a third of the faults unrepairable so refusals stay honest, and makes the rest reachable by exactly one named mechanism, so an arm that fails has nowhere to hide. | docs/RUN1_DIAGNOSIS.md §2, §5, evidence/fault_recoverability.json, evidence/oracle.json |
| 2026-11-15 | Update rule v2: the step becomes asymmetric (`eta_blame` 0.35, `eta_confirm` 0.10) and `cost_floor` rises from 0.05 to 0.5. The run-1 rule is kept as the `full_v1_rule` arm so the change is measured on identical data rather than assumed. | Of the receipts behind the round-1 breaks, 43 of 44 on seed 1 carry only `confirm` signals (40 of 42 on seed 7, 42 of 47 on seed 42): the breaks are caused by confirming correct paths, which makes a shared prefix cheap enough to route a different question into a wrong answer. By round 5, 31%/29%/33% of touched edges sit exactly on the 0.05 floor and about 89% are below 0.2, so the ranking has stopped discriminating and nothing is quarantined after round 3. A symmetric step with a floor two decades below the initial cost converts a correct judgement into collateral damage. | docs/RUN1_DIAGNOSIS.md §6, config/mend.toml |
| 2026-11-15 | Gap-fill v2 triggers on wrong answers as well as unreachable ones and follows a second wave from the nodes the first wave reached; it is measured as `gapfill_wide_only` against the narrow `gapfill_only`, so the widening is attributed rather than folded into the headline. | Ingesting every withheld edge is worth **+9.8 points mean** on held-out, and the whole run-1 full arm captured +0.4 of it — about 4% of the available headroom — while `gapfill_only` alone took +2.2. The narrow rule can only fire on the 96-odd unreachable questions and reaches 35 of them (S25 measured 43 with a second wave); the 44–49 train questions that are *wrong* never trigger it at all, including every `recoverable` fault in v2. This reverses the 2026-11-15 decision to keep one wave, which was taken before the headroom was measured. | docs/RUN1_DIAGNOSIS.md §5, REALITY_SPIKES S25, src/trailmend/loop/gapfill.py |
| 2026-11-15 | H1 is replaced for run 2 by a paired per-question test (two-sided exact McNemar, `full_v2` against `frozen`, same seed, same held-out questions, round 5, p < 0.05 and ≥ 2.0 points on 4 of 5 seeds) instead of comparing the per-seed delta against the spread between seeds. | Run 1's H1 required the lift to exceed the spread across seeds at round 0, which was 2.9 points. That spread measures how different three generated companies are from each other; it is not the noise in a within-seed before/after delta, and it does not shrink as the mechanism improves. A test that can be failed by generating a more varied company is not a test of the Mend. The paired test compares the same questions on the same graph, which is the comparison the claim actually makes. Run 1's H1 verdict is not restated under the new rule. | docs/RUN1_DIAGNOSIS.md finding 5, PRD §3.2 |
| 2026-11-15 | Run 2 adds the held-out wrong-answer rate as a preregistered secondary metric (H6': it falls by ≥ 40% from round 0 to round 5, every seed), and H7' holds gap-fill to ≥ 60% of the withheld edges its own rule can reach. | Measured on held-out under the oracle: quarantining every planted wrong edge moves seed 1 from 27 wrong and 23 unreachable to 14 wrong and 36 unreachable at **identical** accuracy. In the full arm the train questions whose chosen path ran over a planted wrong edge went from 28/31/33 to **0** while the count of planted-wrong-edge failures did not move (33/35/38) — the bad edges stopped being walked and not one of those questions became correct. Accuracy, by itself, scores the whole of that at zero, and run 1 could only express it as a loss. For the person being paged a refusal and a confident wrong name are not the same event, so the run states the distinction up front rather than discovering it in the diagnosis. | docs/RUN1_DIAGNOSIS.md §1, PRD §3.2 |
